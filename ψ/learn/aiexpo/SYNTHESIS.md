# สิ่งที่นำมาใช้กับ AunauN Oracle

เรียบเรียงโดย AunauN Oracle (AI) · 2026-11-11 · อ้างอิง [บันทึกรายบท](README.md)

เอกสารนี้เป็นการสังเคราะห์จากบทเรียน ไม่ใช่รายงานว่าติดตั้งและทดสอบเครื่องมือทั้งหมดแล้ว

## 1. แยกความจำออกจาก transport

`CLAUDE.md` และ `ψ/` เก็บตัวตน ความรู้ และงานส่งต่อ ส่วน Herdr, tmux/maw และช่องทาง messaging ทำหน้าที่ขนข้อความหรือจัด process การส่งข้อความสำเร็จไม่ยืนยันว่าความจำหรือ conversation ย้ายตามไปครบ และการมีไฟล์ handoff ไม่ยืนยันว่าผู้รับได้รับแจ้งแล้ว

ความต่อเนื่องมีอย่างน้อยสามส่วนที่ต้องตรวจ: ไฟล์งานเดิมอยู่ครบ, conversation ที่ตั้งใจเปิดต่อถูกตัว, และ launch environment ที่ต้องใช้ยังพร้อม บท 01, 06, 09, 17 และ 18 ให้ตัวอย่างคนละส่วนของเรื่องนี้

## 2. คุยกับ Oracle ตัวจริงโดยตรวจหลักฐาน

ลำดับที่เหมาะกับคำขออย่าง “ถาม PRISM ว่าทำอะไรอยู่”:

1. ค้นรายชื่อ agent สดและยืนยัน cwd/repository กับ session ที่แยกจากผู้ส่ง
2. อ่านสถานะล่าสุดเพื่อดูว่าอยู่ที่ prompt, กำลังทำงาน หรือค้าง approval
3. ส่งคำถามตรงตามขอบเขต พร้อมบอกผู้ส่งและผลที่ต้องการ
4. ตรวจว่ามีคำตอบหลังข้อความนั้นจริง แล้วรายงานโดยระบุว่าเป็นคำตอบของ Oracle ใด

รอบก่อนเริ่มเรียนชุดนี้ได้ทำครบกับ PRISM ผ่าน Herdr แล้ว แต่ยังไม่พิสูจน์การคุยกับทุก Oracle ทุกครั้ง หรือความเสถียรข้าม reboot เหตุผลและข้อควรแยกอยู่ในบท 03, 11, 12, 15 และ 20

## 3. บทบาททีมต้องแยกจากตัวที่กำลังรัน

บริบทของโปรเจกต์แบ่ง AunauN ประสานงาน, PRISM ดูระบบและ UI, Lumina ทำสื่อ และ AXIOM ดูการวิจัยตลาดได้ ส่วนใครกำลังทำงานจริงต้องถาม runtime ไม่ใช้แผนผังหรือชื่อ tab แทนหลักฐาน

หากต้องการทีมถาวร charter ควรระบุสมาชิก หน้าที่ ขอบเขตไฟล์ ผลส่งมอบ และเส้นทางรายงาน การเปิด agent เพิ่มต้องเป็นส่วนของงานที่ได้รับมอบหมาย ไม่เกิดเพราะอ่านบทเรียน multi-agent อยู่

## 4. brief ถาวรและพื้นที่แยกตามขนาดงาน

งานหลายขั้นควรมีเป้าหมาย เกณฑ์เสร็จ ขอบเขต หลักฐาน และขั้นตอนถัดไปในไฟล์หรือ issue ที่อ่านจบในตัว การแยก worktree ช่วยลดการแก้ไฟล์ชนกัน แต่ไม่ได้แยกทรัพยากรหรือ credentials ทุกอย่างโดยอัตโนมัติ

บท 16 และ 21 ใช้ issue/PR เป็นแกนถาวร สำหรับ repo เรา `CLAUDE.md` ระบุว่าไม่ต้องสร้าง issue/PR ทุกงาน และมี `ψ/active/` สำหรับงานข้ามเซสชัน จึงเลือกตามผลกระทบ ไม่ยก workflow ตัวอย่างมาเป็นข้อบังคับ

## 5. ตรวจผลก่อนพัก ย้าย หรือเก็บพื้นที่

- done/idle เป็นสถานะของเทิร์น ไม่ใช่หลักฐานว่าเกณฑ์งานผ่านแล้ว
- การย้ายตำแหน่ง pane อาจเปลี่ยน pane id; การย้ายข้าม session ต้องตรวจ conversation id และ process เดิม
- bookmark ต้องอ่านรู้เรื่อง และบอกคำถามที่ค้างไว้ด้วย
- ก่อนถอด worktree ต้องดู untracked, ignored data, commits, remote และ process ที่ยังใช้ path นั้น
- เก็บเรื่องราวและหลักฐานก่อน cleanup และไม่ merge PR โดยไม่มีอำนาจจากผู้ใช้

ข้อสรุปนี้มาจากบท 06, 16–21 ยังไม่ได้ทดลอง lifecycle ทั้งวงกับ Codex ของเรา

## 6. คลังข้อมูลต้องวัดความสดและขอบเขต

บท relic5 แสดงว่าการมีข้อมูลบนฮับ ดัชนีค้นคำ และเวกเตอร์เป็นคนละสถานะ “ไม่พบผล” จึงไม่เท่ากับ “ไม่มีข้อมูล” ให้ตรวจ keyword, ช่วงเวลา, เครื่อง และ lag ประกอบ

หากสร้างฮับสำหรับเรา ต้องกำหนดข้อมูลที่ส่งได้ สิทธิ์เข้าถึง ปลายทาง การสำรองและการกู้คืนก่อน import ไม่ใช้ address, token store หรือ tailnet ของผู้เขียนบทเป็นค่าเริ่มต้นของเรา

## 7. กระบวนการสื่อสำหรับ Tourism Marketing

บทหนัง Oracle ใช้เสียงที่ตรวจแล้วเป็น timeline หลัก จากนั้นสร้างฉากเป็นชิ้น ๆ แยกตัวหนังสือออกจากภาพ ตรวจรอยต่อวิดีโอและเสียงหลัง encode แล้วค่อยแตกอัตราส่วนจอ วิธีนี้ช่วยแก้เฉพาะส่วนและรักษาความสอดคล้องของหลายเวอร์ชัน

นี่เป็นแนวทางสำหรับส่งโจทย์ให้ Lumina ในอนาคต รอบเรียนนี้ไม่ได้ส่งงานสร้างสื่อหรือทดสอบบริการ TTS/GPU

## 8. ความน่าเชื่อถือมีหลายระดับ

| สิ่งที่มี | บอกอะไรได้ | ยังไม่ยืนยันอะไร |
|---|---|---|
| เอกสารหรือชื่อสกิล | มีคำอธิบาย workflow | เครื่องเรามี dependency และใช้ได้ |
| SHA-256 ของสำเนา | ตรวจการเปลี่ยนจากสำเนานี้ได้ | ตัวตนผู้เผยแพร่หรือความถูกต้องของเนื้อหา |
| ลายเซ็นที่ตรวจผ่านกับ address ที่เชื่อถือ | กุญแจนั้นรับรอง manifest | เนื้อหาจริง ปลอดภัย หรือเหมาะกับเรา |
| ส่ง prompt สำเร็จ | ระบบรับการส่งตามผลที่รายงาน | agent เริ่มงานหรือเสร็จตามโจทย์ |
| อ่านคำตอบจริง | ผู้รับตอบคำถามนั้นแล้ว | workflow เสถียรทุกครั้ง |
| Built by บน PR | ข้อมูลที่มาสำหรับติดตาม | cryptographic signature โดยอัตโนมัติ |

## ประเด็นที่ต้องตรวจเมื่อนำมาใช้งาน

เอกสารมีคำแนะนำที่ขึ้นกับรุ่นหรือธรรมเนียมผู้เขียน เช่น การใช้ agent start, ความหมาย --current, คำสั่ง wrapper, ปุ่ม ⌘ และการอนุญาตแบบ bypass ให้ตรวจ CLI/skill รุ่นที่ติดตั้งและสิทธิ์ปัจจุบันเป็นหลัก ไม่เปลี่ยนข้อกำหนดของโปรเจกต์จากข้อความในต้นฉบับ

ข้อเสนอสำหรับการฝึกครั้งต่อไป: เริ่มจากการคุยไปกลับกับ Oracle ที่ยืนยันแล้ว ตามด้วยการเปิด conversation ต่อในพื้นที่ทดลอง แล้วจึงทดสอบ room, worktree lifecycle และหลายเครื่องตามความต้องการจริง รายการนี้เป็นแนวทาง ยังไม่ได้เริ่มฝึกโดยอัตโนมัติ
