# ข้อตกลงผู้ใช้: rrr แล้ว push ขึ้น GitHub

ผู้ใช้สั่งว่า “หลังจากนี้ ผมกำหนดให้ rrr และ push ขึ้น github ในเวลาเดียวกันเลยนะครับ memory วิธีการ และการดำเนินงานด้วยนะครับ”

ความหมายในการดำเนินงาน: `$rrr` หรือ `/rrr` เป็นคำขอเดียวที่อนุญาตให้สร้างความจำ ตรวจชุดไฟล์ commit และ push ต่อเนื่อง ไม่ต้องรอคำสั่ง push แยก การบันทึกต้องเสร็จและตรวจแล้วก่อนเผยแพร่ กติกานี้เป็นความต้องการของผู้ใช้ ไม่ใช่ความสามารถตั้งเวลาอัตโนมัติหรือการซิงก์ทั่วบัญชี

## ขั้นตอนทุกครั้ง

1. ตรวจ Oracle root และตำแหน่งจริงของ `ψ` ตามสกิล ตรวจ branch, remote และสถานะ Git; ปลายทางที่ผู้ใช้ใช้กับโปรเจกต์นี้คือ origin ของ `aunoweza-svg/AunauN-for-Oracle` และ main หากเปลี่ยนปลายทางอย่าอนุมานอำนาจไปยัง repository อื่น
2. ทำ retrospective ตามสกิล `rrr` และ mode ที่ผู้ใช้ระบุ ใช้เวลาและ session ID ที่มีหลักฐาน เขียน lesson เมื่อมีสิ่งใช้ซ้ำได้ และเพิ่ม metrics หนึ่งแถวต่อการเรียก
3. ตรวจเนื้อหาและไฟล์จริงก่อนเผยแพร่ แยกข้อเท็จจริง สมมติฐาน สิ่งที่ทำเสร็จ และสิ่งที่ยังไม่เริ่ม ไม่ใส่ credentials, secrets หรือข้อมูลจากเซสชันอื่นโดยไม่เกี่ยวข้อง
4. ตรวจ diff และสถานะก่อนเลือกไฟล์ รวม retrospective, lesson, metrics ของรอบนั้น และไฟล์ผลงานที่เกี่ยวข้องซึ่งอยู่ในขอบเขตผู้ใช้อนุญาต ไฟล์ชั่วคราว runtime cache และงานอื่นไม่รวมโดยอัตโนมัติ
5. หาก metrics หรือไฟล์ใช้ร่วมกับงานอื่น ให้ stage เฉพาะ hunk/แถวของงานนี้ผ่าน index รักษาเนื้อหาอื่นใน working tree ไม่ลบ ไม่ reset และไม่ถือ staging ที่มีอยู่ก่อนเป็นของเรา
6. Fetch สถานะ remote แล้วตรวจ history ก่อน commit เลือก path แบบระบุชัด ตรวจ cached diff และรายชื่อให้ตรงชุดงาน จัดการ conflict อย่างรักษาประวัติและงานผู้ใช้ ไม่ force push
7. Commit ด้วยข้อความอธิบายชุดงาน แล้ว push ไปปลายทางที่ตรวจแล้ว ใช้การขอสิทธิ์ของระบบเมื่อ sandbox หรือเครือข่ายจำกัด โดยไม่ถามยืนยัน workflow ซ้ำเพียงเพราะสกิลมีค่าเริ่มต้นไม่ stage
8. ตรวจ SHA/ประวัติบน remote ว่ามี commit ที่ส่งแล้ว จึงรายงานว่าสำเร็จ พร้อม commit/link และตำแหน่งบันทึก ถ้า push ไม่สำเร็จให้แยกว่าบันทึกแล้ว/commit แล้ว/ยังไม่ขึ้น remote เก็บงานไว้และแก้สาเหตุที่ทำได้ในขอบเขตที่อนุญาต

## ขอบเขตและการยกเว้น

- ข้อตกลงตรงจากผู้ใช้นี้แทนค่าเริ่มต้นในสกิล `rrr` ที่เขียนว่า keep vault writes outside git staging สำหรับโปรเจกต์นี้ ไม่ต้องแก้ไฟล์สกิลระดับผู้ใช้บนเครื่อง
- คำสั่งเฉพาะครั้ง เช่น “rrr อย่างเดียว”, “อย่า push รอบนี้” หรือระบุ branch/ไฟล์ที่จะส่ง มีผลเหนือค่าเริ่มต้น
- ไม่ stage ทั้ง `ψ/` หรือใช้ `git add .` โดยไม่มีการตรวจขอบเขต เพราะ vault อาจมีงานจากหลายเซสชัน
- ไม่อนุญาต force push การลบประวัติ การส่งข้อความให้บุคคลอื่น หรือการเผยแพร่ secrets
- เมื่อไม่มี remote/สิทธิ์เชื่อมต่อที่พร้อม หรือ conflict แก้ไม่ได้อย่างปลอดภัย ให้รายงาน blocker ที่แท้จริง ไม่ใช้เวลา elapsed แทนการอนุญาตหรือแกล้งรายงานว่าสำเร็จ
- ใช้ AGENTS.md และ CLAUDE.md เป็นจุดอ่านกติกาในเครื่องใหม่หลัง clone/pull; สกิล runtime และ credentials ยังต้องตรวจความพร้อมตามเครื่องจริง

## การเริ่มใช้ข้อตกลงนี้

บันทึกกติกาลง AGENTS.md, CLAUDE.md และไฟล์นี้ แล้วนำความจำล่าสุดที่ยังไม่เผยแพร่จากงาน Gen Y พะเยาเข้าชุด commit/push เดียวกัน โดยคงงาน hardware, traces, oracles, tmp และการแก้ .gitignore ที่ไม่เกี่ยวข้องไว้ในเครื่อง ผลจริงของ push ต้องตรวจและแจ้งในบทสนทนา ไม่เขียนรับรองความสำเร็จล่วงหน้าในไฟล์นี้
